# Правила для ИИ-ассистентов и авторов кода

Проект: скрипты обработки и визуализации MRI-данных (TCP/UCLA), Python 3.14.
Код пишет несколько человек, и каждый читает то, что не писал сам. Поэтому
код должен быть понятен без контекста твоего чата: типы и документация
обязательны, а не «по возможности».

## Проверка перед «готово»

```sh
ruff format
ruff check --fix
basedpyright
```

Исправляй код, а не правила: не добавляй `# noqa`, `# type: ignore` и
исключения в `pyproject.toml`, чтобы проверка «прошла». Если без исключения
никак, укажи код правила и причину в той же строке и скажи об этом человеку.
Настройки линтеров и форматтера (`pyproject.toml`, `.editorconfig`) не меняй,
пока человек явно не попросил.

## Правила кода

1. **Формат.** Не больше 90 символов в строке: код, комментарии и
   докстринги. Форматирует `ruff format`, вручную выравнивать код не нужно.
2. **Типы.** Аннотируй все параметры и все возвращаемые значения, включая
   `-> None`. Переменные аннотируй там, где тип не очевиден из
   присваивания. Массивы: `numpy.typing.NDArray[np.float64]` (dtype
   указывай). `Any` только с комментарием, почему иначе нельзя.
3. **Документация.** Докстринг у каждого класса, функции и метода, включая
   приватные (`_name`) и вложенные. Он должен отвечать на вопрос «что это
   делает и чего ждёт на входе» так, чтобы хватило при наведении курсора в
   редакторе, без чтения тела. Докстринг модуля не обязателен.
4. **Константы и атрибуты.** Строка-докстринг сразу под присваиванием (для
   констант модуля, полей класса и dataclass). Редактор покажет её при
   наведении.
5. **Пути и константы.** Только `pathlib`. Пути, имена файлов и пороги не
   размазывай по коду: бери из модуля с константами, а не пиши литералами.
   Абсолютных путей в коде нет.
6. **Комментарии.** `#` объясняет, **почему** так сделано, а не что
   делает строка. Закомментированный код не оставляй: он есть в git.
7. **Минимальный дифф.** Меняй только то, что нужно для задачи. Чужие
   файлы переформатируй отдельным коммитом, не вместе с правкой логики.
8. **Данные и окружение.** Не коммить `.venv`, данные и результаты
   обработки. Исходные CSV/NPZ не редактируй вручную.

## Как оформлять докстринги

Стиль Google. Первая строка: одно предложение, которое
заканчивается точкой. Дальше при необходимости детали, затем `Args:`
(по строке на каждый параметр: смысл, единицы, форма массива, допустимые
значения), `Returns:` и `Raises:`.

Пример (проходит все проверки проекта):

```python
import numpy as np
from numpy.typing import NDArray

SMOOTHING_FWHM_MM: float = 6.0
"""Ширина сглаживающего ядра (FWHM), мм."""


def zscore(
    values: NDArray[np.float64],
    axis: int = 0,
) -> NDArray[np.float64]:
    """Стандартизует значения вдоль оси (z-оценка).

    Args:
        values: Матрица признаков, форма ``(субъекты, признаки)``.
        axis: Ось, вдоль которой считаются среднее и разброс.

    Returns:
        Массив той же формы; среднее вдоль ``axis`` равно 0, стандартное
        отклонение равно 1. Срезы с нулевым разбросом дают 0.

    Raises:
        ValueError: Если ``values`` пуст.
    """
    if values.size == 0:
        msg = "values не должен быть пустым"
        raise ValueError(msg)
    std = values.std(axis=axis, keepdims=True)
    centered = values - values.mean(axis=axis, keepdims=True)
    return np.divide(centered, std, out=np.zeros_like(centered), where=std > 0)
```

Поле dataclass с докстрингом:

```python
@dataclass
class Settings:
    """Параметры отбора субъектов."""

    threshold: float = 0.5
    """Минимальное качество скана, 0..1; ниже субъект исключается."""
```
